platform admin creates gyms and owners; owners create members and

and progress; owners see that data and receive AI-generated insights;

## 2. Final architecture

FastAPI (sync, SQLAlchemy 2.x ORM) behind a thin router layer; every router
delegates to a service module that owns all business logic and tenant
scoping. Celery + Redis handle scheduled/background work. PostgreSQL is the
single source of truth; Alembic manages schema migrations.

Tenant isolation is enforced in exactly one place per request:
`require_tenant_gym_id` / `AuthContext.gym_id`, both derived solely from
the authenticated session — never from a client-supplied parameter. Every
service function that reads or writes tenant-owned data takes `gym_id` as a
required keyword argument and filters by it in the query itself (not
"fetch then check").

```
React Native (not built) -> API Client -> FastAPI -> Service Layer -> SQLAlchemy -> PostgreSQL
                                                    -> Celery -> Redis -> Worker -> PostgreSQL / AI provider
                                                    -> Celery Beat -> Celery -> Worker
```

## 7. AI implementation

`PostgreSQL → build_member_summary → build_prompt → [AI provider] →
parse_and_validate_ai_response → AIInsight row`. The provider call
(`app.ai.client.call_ai_provider`) is the single I/O boundary; every other
function is pure/DB-only. Response validation handles every case section 37
lists: malformed/truncated JSON, non-object JSON, missing fields,
unexpected fields (tolerated, not rejected), empty/None response, timeout,
non-2xx HTTP, hallucinated enum values, wrong types, oversized text. Never
executes arbitrary DB queries or privileged actions from model output.

## 8. Security mechanisms

- Argon2id password hashing; JWTs carry only `sub`/`gym_id`/`role`/
  `session_id`/`type`/`exp` — never passwords or PII
- Server-side session revocation: logout actually invalidates the session
  (checked on every request), not just client-side token deletion —
  verified live, including that a second concurrent session is untouched
- Tenant isolation enforced via gym_id derived from the session, checked at
  the query level on every tenant-scoped read/write
- Cross-tenant IDOR returns `404`, verified indistinguishable from a
  genuinely nonexistent ID (same status, same error code — no oracle)
- RESTRICTED/EXPIRED/CANCELLED members blocked from creating new
  sessions/logs/progress at the backend (never client-side only); a real
  bug here (EXPIRED not originally covered) was found and fixed during the
  harsh-QA pass
- Centralized error handling — no stack traces, DB errors, or internal
  paths ever reach the client

## 11. Known limitations

- **No Docker packaging** (per your request — you're adding this).
- **No mobile app build** — API is fully ready for one; the RN app itself
  wasn't built (see section 1).
- **No live AI provider verified** — pipeline fully built/tested against
  fake responses; the actual network call to a real Gemma Flash Lite (or
  equivalent) endpoint is unverified.
- **N+1 pattern in the dashboard member list** — found during performance
  testing (section 41), bounded by pagination (not a live bug at V1 scale),
  documented with a concrete batching fix in `PERFORMANCE.md`.
- **Connection-pool queuing under concurrency** — expected default-config
  behavior for a single uvicorn process; documented fix path (multiple
  workers, tuned pool size) in `PERFORMANCE.md`.
- **`EXPIRE_AFTER_RESTRICTED_DAYS` (30 days) and "nearing expiry" (3 days)
  thresholds** are my own reasonable choices where the spec didn't specify
  exact numbers — documented inline in `app/memberships/lifecycle.py`.
- **No idempotency-key mechanism** for double-submitted requests (e.g. two
  identical payment POSTs both succeed independently) — not in the spec's
  required scope, current behavior is explicitly pinned down by a test
  rather than left undefined.
- **`generate_periodic_analytics`** writes snapshots to `audit_logs` rather
  than a dedicated table, since section 4's schema list doesn't include
  one — a deliberate minimal-footprint choice, documented in
  `app/analytics/service.py`.
- Sandbox-specific: this development environment's Postgres/Redis
  processes don't persist between conversation turns (data on disk
  survives; the server processes need restarting) — irrelevant to the
  actual deliverable, just a note on how this was built/verified.
